# Automated execution and handoff runbook

The agent should continue the active milestone autonomously within authorized
scope, with short progress updates, but must stop at a real missing dependency
or required hardware evidence. Do not turn absence of a response into permission,
waive tasks, or fabricate proof. This is a development runbook; full game build,
deployment and hardware testing are not implemented automation yet.

## Resume deterministically

```bash
git status --short --branch
git remote -v
git submodule status
git log -5 --oneline
```

Read AGENTS.md, MILESTONES.md, PORT_DISCOVERY.md, current milestone evidence/review
and prior review findings. Confirm exactly one active milestone branch, pinned
upstream and no unowned changes. Preserve unrelated user changes. If a branch is
already active, resume it; do not restart/rebase away review history.

## M00 discovery (available now)

```bash
python3 -m venv build/discovery-tools
build/discovery-tools/bin/python -m pip install -r tools/discovery-requirements.txt
build/discovery-tools/bin/python tools/discover_port.py --iso /absolute/path/to/user-disc.iso
python3 tools/validate_project.py
python3 -m unittest discover -s tools -p 'test_*.py' -v
```

On Windows use the venv's `Scripts/python.exe`. `--iso` is explicit; never scan
other user drives or download assets. Generator reads ISO directory metadata
and supported executable identity only, emits no game bytes. Its supplied parser
index has recorded gaps, so do not treat it as a full semantic compiler index.
CI validates the committed metadata without requiring the user's ISO.

Discovery rerun is required after submodule/config/source scope changes; evaluate
the diff, refresh counts/ownership and run checks before the active milestone's
review. Do not replace old behavioral evidence merely by regenerating metadata.

## Per-task execution algorithm

1. Select the earliest unchecked task of the active milestone whose prerequisites
   are satisfied. Resolve its exact owning files via the discovery inventory and
   source, not by blindly editing every portability candidate.
2. Record expected result and appropriate proof before implementation. Use the
   smallest coherent change; preserve numerical/game/reference behavior.
3. Run relevant build/tests/reference comparison. Save raw output privately under
   `build/evidence/Mxx/task-id/` and a concise tracked sanitized result/report.
   For screenshots/audio generated by the game, retain them privately and commit
   metadata/hash/observation references rather than copyrighted asset payloads.
4. Update evidence.json with the tracked report path/result and mark its checkbox
   only after observed acceptance. Missing environment/device -> unchecked task,
   concise blocker report, continue only independent tasks in the same milestone.
5. Commit coherent work on the milestone branch; push it. A draft PR may run CI
   during implementation. This does not create an independent reviewer.
6. Run earlier relevant regression proof after any owning-layer change. Capture
   failures and fixes; never erase failing proof to make a task appear complete.

Suggested maintained build interfaces to implement in M01/M02 (NOT available yet):
noninteractive `tools/build_switch.py`, source/toolchain lock validation,
host-generation command, private asset preparation, target deployment/log capture
and deterministic gameplay route execution. These names are design targets, not
commands the current repo claims to provide. Until implemented use AGENTS.md's
explicit CMake commands inside the verified toolchain.

## Review creation gate (available now)

```bash
# After tasks, evidence, local validation and foundation CI pass:
python3 tools/milestone_gate.py M00
git rev-parse HEAD
```

The gate rejects wrong branch, unchecked tasks, missing/extra task evidence keys,
malformed/blank narratives, Git-internal/ignored/untracked/link evidence, evidence
whose content differs from its regular committed HEAD blob, and a dirty working
tree. Only after PASS create a
fresh independent reviewer agent. No reviewer agent for another milestone while
any task of that milestone remains incomplete. Implementation agents are not
authorized merely by this runbook; the user specifically authorized the reviewer.

Reviewer brief template:

> Review milestone Mxx at exact candidate SHA ... independently. All implementation
> tasks are marked complete and the eligibility gate passed. Read AGENTS.md,
> docs/MILESTONES.md, discovery and task evidence. Do not edit files or merge.
> Verify every task, run applicable checks, inspect implementation against owning
> source and challenge overclaims. Report APPROVE or REQUEST_CHANGES with precise
> findings and actual test/limitation details. This milestone does/does not require
> Switch hardware. Do not substitute unavailable proof or waive a task.

If changes are requested, reopen tasks before fixing, complete/recheck them, then
request independent review of the new candidate. Do not carry approval across
source/evidence/task changes. No time-based auto-approval or reviewer averaging.

## Review record, merge and next branch

After an actual independent approval, record its exact result in
`docs/milestones/Mxx/review.json`. Required fields: milestone, candidate_commit,
verdict=`APPROVE`, reviewer_id, independent=true, unresolved_findings=[], checks
(nonempty list of nonblank text), limitations (list of nonblank text, explicitly
empty only if none), and observed_test_results (nonempty list of nonblank text).
No invented reviewer ID
or a claim that an external person approved. An independent agent is not a GitHub
account PR approval; do not impersonate one.

Only that review JSON may change after the candidate; commit/push it, then:

```bash
python3 tools/milestone_gate.py M00 --require-review
gh pr checks <PR-number> --watch
gh pr merge <PR-number> --merge --delete-branch
git switch main
git pull --ff-only origin main
git switch -c milestone/m01-platform-smoke
git push -u origin milestone/m01-platform-smoke
```

Use the corresponding next branch from MILESTONES.md. Run commands sequentially,
stop on failure and verify the PR merge SHA/remote main before creating the next
branch. Do not use admin bypass/force push or merge a failing PR. The user has
authorized this milestone flow; routine successful merges need no repeated
permission request. No tag/release before M11's review gate and release checks.

## CI and repository controls

`foundation.yml` runs source-only inventory/asset-policy and governance tests on
push/PR. `milestone-review` additionally validates recorded completed tasks and
exact-candidate review for a milestone PR into main. It is expected to fail while
tasks/review are incomplete. Passing it proves record consistency, not gameplay.

GitHub branch protection is attempted for main. If the private-repo plan rejects
it, record that limit; CI still reports status and the agent still must obey the
workflow, but server-side merge prevention is not guaranteed. Never claim the
review record cryptographically proves reviewer independence. Treat the reviewer
conversation and its reproduced evidence as the actual independent evaluation.

Source-only CI never gets ISO/ELF/generated game C++/user saves. Full game builds
require local or explicitly configured private self-hosted runners with private
inputs. Never upload those inputs as GitHub Actions artifacts. Hardware automation
requires a real connected supported device/transport and an observable log/input
channel. If unavailable, report the exact unchecked task and pause dependent work.

## Failure recovery

- Configure/compiler/library failure: preserve complete log, classify host vs
  target dependency, fix owning build layer, retry changed input. No host-library
  substitution or disabling correctness checks to get a binary.
- Guest hang: save state/last scheduler/IOP/streaming markers, compare host trace,
  inspect exact function path; use REA only for an unanswered binary question.
- Rendering failure: isolate RHI feature/shader/state/resource lifetime and compare
  reference readback before changing game logic or introducing a new graphics API.
- Audio failure: inspect device identity, producer progress, queue/underruns and
  real PCM; nonzero samples or silence do not establish audible correctness.
- Lost device/control: leave hardware task unchecked; do not infer a pass from
  emulator/title-screen behavior. Preserve deployment and last known good binary.
- Failed review: reopen findings/tasks on same branch, fix, rerun proof, new review.
- Interrupted session: resume current branch/evidence; never advance the milestone
  merely because another chat started or the task ran for a long time.
